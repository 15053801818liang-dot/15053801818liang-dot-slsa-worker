4. 仓库级合规与加固检查表（手动配置项）

⛔ 反模式警告 — 切勿为"让溯源生效"而放宽全局权限

流传的一种错误做法是：把 Settings → Actions → General → Workflow permissions 设为 "Read and write permissions"， 并勾选 "Allow GitHub Actions to create and approve pull requests"，理由是"确保 OIDC 与 Attestations 权限生效"。 该做法技术上不必要，且直接违反 SLSA L3 的最小权限要求。

错误主张官方文档事实
需放宽全局权限，OIDC/Attestations 才生效 权限"初始值取自企业/组织/仓库默认，随后由工作流文件先在 workflow 级、再在 job 级调整"。本流水线已在 provenance job 显式声明 id-token: write + attestations: write，无需放宽仓库默认值。文档明确："拥有仓库写权限者可通过编辑工作流的 permissions 键增删权限。"
只读默认会阻断 id-token id-token 从不随读写开关自动授予——未在 permissions 中显式指定的范围一律为 none（"all of those that are not specified are set to none"）。因此它只能靠显式声明获得，放宽全局开关对其无帮助。
需勾选"create and approve pull requests" 该开关仅控制 GITHUB_TOKEN 能否创建/批准 PR，与溯源生成零关联。个人账号新仓库默认关闭。开启后允许 Actions 自动批准 PR，等于绕过双人审查——直接摧毁 SLSA 的源码审计控制。

依据：GitHub Docs — "Use GITHUB_TOKEN for authentication in workflows" / "Managing GitHub Actions settings for a repository" / "Workflow syntax — permissions"（2026-08-09 核实）。

✅ 正确结论：本流水线已通过 Job 级 permissions 声明实现最小权限加固。仓库层面的 Workflow permissions 应保持或收紧为只读（个人账号新建仓库默认即为 contents/packages 只读），无需任何全局提权。 注意：组织内新建仓库的该设置继承自组织配置——若组织默认为 Read and write，应主动收紧为只读，而非"保持默认"。
